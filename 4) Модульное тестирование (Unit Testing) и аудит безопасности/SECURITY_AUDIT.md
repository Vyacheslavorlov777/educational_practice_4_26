# Аудит безопасности: защита от SQL-инъекций

## Область проверки

Все SQL-запросы приложения (`db.js`, `partnerService.js`) — окно добавления/редактирования
партнера, история продаж, получение списка партнеров. Отдельной формы поиска/авторизации
в приложении нет, поэтому проверке подлежат все точки, где пользовательский ввод попадает в БД.

## Результат

Все запросы используют параметризованные подготовленные выражения `db.prepare(sql).run(...)` /
`.get(...)` / `.all(...)` с плейсхолдерами `?`. Пользовательские значения никогда не подставляются
в текст SQL-запроса через конкатенацию строк или шаблонные литералы.

Пример из `partnerService.js`:

```js
// Правильно: значения передаются отдельно от текста запроса
db.prepare(`
  INSERT INTO partners (partner_type, name, rating, address, director, phone, email)
  VALUES (?, ?, ?, ?, ?, ?, ?)
`).run(data.partnerType, data.name, data.rating, data.address, data.director, data.phone, data.email);
```

Так делать было бы небезопасно (в проекте такого кода нет, пример приведен для сравнения):

```js
// Небезопасно: прямая конкатенация пользовательского ввода в SQL
db.exec(`INSERT INTO partners (name) VALUES ('${data.name}')`);
```

Единственные места, где ID подставляется напрямую (без `?`), — регулярные выражения маршрутизации
(`req.url.match(/^\/api\/partners\/(\d+)$/)`), которые уже ограничивают значение только цифрами
до того, как оно попадет в `Number(...)` и далее в параметризованный запрос.

## Вывод

Критических уязвимостей SQL-инъекции не обнаружено. Рекомендация — сохранять это правило
(только параметризованные запросы) при добавлении новых точек работы с БД в будущем.
